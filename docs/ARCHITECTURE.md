# 설계와 동작 원리

## 전체 구조

`MiniRedis`는 다음 세 가지 구조를 함께 관리합니다.

1. 데이터 해시맵: 키로 값, 메모리 크기, LRU 노드, 만료 시각 등의 항목 정보를 찾습니다.
2. LRU 이중 연결 리스트: 앞쪽은 가장 최근에 사용한 키, 뒤쪽은 가장 오래 사용하지 않은 키입니다.
3. TTL 최소 힙: `(expire_at, key)`를 만료 시각 순으로 보관합니다. 별도 해시맵은 키별 힙 인덱스를 보관합니다.

`CommandProcessor`는 문자열을 파싱하고 인수를 검증한 뒤 저장소 메서드를 호출합니다. `cli.py`는 입력과 출력만 담당합니다. 자료구조는 `structures/`의 독립 모듈로 분리했습니다.

## 동적 배열

`DynamicArray`는 `[None] * capacity`로 고정 길이 공간을 확보합니다. 사용 중인 길이와 할당된 용량은 별도로 관리합니다. 공간이 차면 2배 크기의 새 공간을 만들고 기존 항목을 인덱스로 복사합니다. Python 리스트의 자동 `append` 확장에 의존하지 않습니다.

인덱스 접근과 치환은 O(1)입니다. `append`는 확장 시 O(n), 평균 분할 상환 O(1)입니다. 중간 항목을 삭제하면 뒤 항목을 이동하므로 O(n)이며, 끝 항목 삭제는 O(1)입니다. 해시맵 버킷 배열과 힙의 내부 저장소에 이 구조를 재사용합니다.

## 해시맵과 충돌 처리

키를 UTF-8 바이트로 변환한 뒤 64비트 FNV-1a를 계산합니다.

```text
hash = 14695981039346656037
각 byte에 대해:
    hash = hash XOR byte
    hash = (hash * 1099511628211) AND 0xFFFFFFFFFFFFFFFF
bucket_index = hash % capacity
```

같은 버킷으로 들어온 서로 다른 키는 이중 연결 리스트에 `(key, value)`를 넣는 체이닝으로 해결합니다. 조회 시에는 해당 버킷만 순회하며 키를 직접 비교합니다. 기존 키의 `put`은 값을 교체하고 크기를 늘리지 않습니다.

새 키를 넣은 후 `size / capacity > 0.75`이면 버킷 수를 2배로 늘립니다. 버킷 수가 바뀌면 나머지 연산 결과도 달라지므로 모든 항목을 새 버킷으로 다시 배치합니다. 해시 조회·삽입·삭제는 평균 O(1)이지만, 충돌이 한 버킷에 몰린 최악의 경우 O(n)입니다. 확장 작업도 O(n)이므로 삽입의 평균 비용은 분할 상환 관점에서 설명합니다. 해시 계산에는 키의 UTF-8 바이트 수에 비례하는 시간이 추가됩니다.

## O(1) LRU 추적

이중 연결 리스트의 노드는 `data`, `prev`, `next`를 갖습니다. 리스트는 양 끝 노드와 길이를 유지합니다. 해시맵의 데이터 항목이 자신의 LRU 노드를 직접 참조하므로 키를 찾은 뒤 리스트를 다시 탐색하지 않습니다.

- 새 `SET`: 앞쪽에 노드를 삽입합니다.
- 기존 키의 `SET` 또는 성공한 `GET`: 기존 노드를 떼어 앞쪽에 다시 연결합니다.
- 키 삭제: 참조 중인 노드를 직접 제거합니다.
- LRU 제거: 뒤쪽 노드가 가리키는 키를 삭제합니다.

노드 삽입·제거·이동은 포인터 몇 개를 바꾸므로 O(1)입니다. 키의 조회까지 포함하면 해시맵의 평균 O(1) 비용이 추가됩니다. TTL이 있는 키를 삭제할 때는 힙 정리 비용도 필요합니다. 다른 리스트 소유의 노드를 잘못 제거하는 동작은 소유자 검증으로 막습니다.

## TTL 최소 힙

배열로 완전 이진 트리를 표현합니다. 인덱스 `i`의 부모는 `(i - 1) // 2`, 자식은 `2 * i + 1`, `2 * i + 2`입니다. 부모가 자식 이하라는 최소 힙 조건을 유지하면 루트가 가장 빠른 만료입니다. 만료 시각이 같으면 키 문자열 비교로 순서를 결정합니다.

삽입 후 `_heapify_up`, 루트 제거 후 `_heapify_down`을 수행합니다. 별도 사용자 정의 해시맵에 `key -> index`를 기록하므로 특정 키의 TTL 변경이나 삭제에 힙 전체 탐색이 필요 없습니다. 두 힙 항목을 교환할 때 인덱스 맵도 함께 갱신합니다.

`EXPIRE`를 다시 호출하면 그 키의 기존 힙 항목을 교체합니다. `SET`, `DEL`, LRU 제거 시에는 기존 타이머를 실제로 제거합니다. 따라서 이미 삭제되거나 갱신된 과거 만료 항목이 계속 쌓이지 않으며, TTL이 있는 키마다 힙 항목은 하나입니다.

힙의 높이는 O(log n)이므로 삽입·변경·삭제는 해시 조회의 평균 비용을 전제로 평균 분할 상환 O(log n)입니다. 루트 조회는 O(1)입니다. 내부 배열 또는 인덱스 맵 확장이 일어나는 개별 연산은 O(n)이 될 수 있습니다.

만료 시각에는 `time.monotonic()` 기반 시계를 사용합니다. 시스템 날짜를 변경해도 남은 시간이 갑자기 늘거나 줄어들지 않습니다. 시계의 초 값을 정수 나노초로 변환한 뒤 정수 만료 기간을 더하므로, 큰 64비트 초 인수에서도 부동소수점 덧셈으로 초가 소실되는 문제를 피합니다. 테스트에서는 시계를 주입해 실제 대기 없이 경계 시각을 재현합니다.

## 명령 실행과 만료 정리

저장소 작업 전에 현재 시각을 읽고 힙 루트가 만료되었는지 확인합니다. `expire_at <= now`인 동안 루트를 제거하고 데이터·LRU·메모리도 정리합니다. 다음 루트가 미래이면 중단합니다. 따라서 `GET`, `EXISTS`, `KEYS`, `DBSIZE` 등에서 만료된 키가 결과에 포함되지 않습니다.

이 프로그램은 명령 실행 시점에 만료를 정리하며, 별도 백그라운드 스레드는 사용하지 않습니다. 입력이 없는 동안 물리적으로 남아 있는 항목도 다음 명령에서 정리되므로 만료 후 다시 조회할 수 없습니다.

한 번에 만료된 키가 `k`개이면 정리에 평균 O(k log n)이 추가됩니다. 명령의 시간 복잡도를 설명할 때 이 비용을 제외하고 무조건 O(1)이라고 말하면 안 됩니다.

`TTL`은 만료 시각과 현재 시각의 차이를 정수로 내림합니다. 남은 시간이 1초 미만이면 키가 아직 존재하더라도 0을 반환할 수 있습니다. 만료 설정 없는 키는 -1, 없거나 이미 만료된 키는 -2입니다.

## 메모리 계산과 제거 순서

키와 값의 UTF-8 바이트 길이 합계를 저장소 사용량으로 계산합니다. `한`은 UTF-8에서 3바이트이므로 문자 수와 메모리 사용량은 다를 수 있습니다. 만료 시각, 힙, 노드, 버킷 등의 부가 비용은 과제 공식에 따라 제외합니다.

`SET`의 흐름은 다음과 같습니다.

1. 이미 만료된 키를 정리합니다.
2. 새 키와 값만으로 양수 메모리 상한을 넘는지 검사합니다. 넘으면 OOM을 반환하고 기존 값을 유지합니다.
3. 기존 값이 있으면 이전 크기만큼 빼고 새 크기를 더합니다. 기존 TTL은 제거합니다.
4. 저장된 키를 최근 사용 위치로 옮깁니다.
5. 상한을 넘는 동안 LRU 뒤쪽 키를 지우고 `used_memory`를 줄이며 `evicted_keys`를 늘립니다.

모든 키 삭제 경로는 데이터·LRU·TTL·메모리를 함께 정리합니다. 사용자의 `DEL`과 TTL 만료는 `evicted_keys`를 늘리지 않습니다. `CONFIG SET maxmemory`로 상한을 낮춘 경우에도 같은 LRU 제거 절차를 즉시 수행합니다. 상한 0은 무제한입니다.

## 비용 정리

아래 표는 키 길이를 상수로 보고, 만료 일괄 정리 비용을 별도로 둔 평균 또는 분할 상환 비용입니다.

| 작업 | 비용 | 이유 |
| --- | --- | --- |
| 해시 조회 | 평균 O(1), 최악 O(n) | 해당 버킷의 체인 탐색 |
| LRU 노드 이동 | O(1) | 노드를 직접 참조 |
| TTL 없는 `GET`, `EXISTS` | 평균 O(1) | 해시 조회와 선택적 노드 이동 |
| `EXPIRE`, TTL 타이머 제거 | 평균 분할 상환 O(log n) | 힙 위치 탐색과 상향·하향 정렬 |
| LRU 키 `e`개 제거 | 평균 O(e log n) 상한 | 각 항목의 TTL 정리 포함 |
| 만료 키 `k`개 정리 | 평균 O(k log n) | 루트부터 순서대로 제거 |
| `KEYS` | O(n + b) | 항목과 버킷 `b`개 순회 |
| `DBSIZE`, `INFO memory` 본체 | O(1) | 유지 중인 카운터 사용 |

해시맵은 축소하지 않으므로 현재 키 수가 작더라도 과거에 확장된 버킷 수 `b`가 클 수 있습니다. `KEYS`의 엄밀한 순회 비용에는 이를 포함합니다. 문자열 파싱, UTF-8 변환, 결과 출력에는 입력·출력 문자열 길이에 비례하는 비용도 추가됩니다.
